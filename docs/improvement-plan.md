現行構成は [architecture.md](architecture.md)、robotの既存機能は [robotの設計文書](../../robot/docs/architecture.md) を参照する。

## 目的と前提

- 5アプリの既存動作を確認しながら、構成・管理方法を改善する。
- 機能からソースへたどれる案内を整え、全ファイルの記憶に頼らず変更できるようにする。
- robotの全機能をuroaへ組み込むというユーザーの方針に対応する。ブラウザー、AIサーバー、ESP32ファームウェアは実行環境ごとに責任を分ける。
- 単一リポジトリ化は推奨案。履歴の取り込み方式、最終的な配置、教材仕様は未決定。
- ユーザーによると、planeのall_functions.tsはnamespaceからモジュールへの移行時に循環参照を回避するため作られた。既存のimport type、AppServices、生成関数登録を維持・整理することを分割の前提とする。
- robotのchat、BLEサーボ・IMU、DCモーター復旧確認は現在独立している。AI回答から直接モーターを動かす機能や、2種類のファームウェアの統合は既存仕様ではない。

## P0: 機能の案内と基準の作成

1. docs/features.mdを作る。機能、入口・主要関数、関連ソース、教材・資産、確認方法、実装状態を対応させる。全関数を手作業で列挙する形にはしない。
2. 同じ名前の機能を区別する。例: 独立モジュールlessonとmovieのlesson、WebGPUの従来デモとschema方式。
3. 5アプリごとに再現用の教材・問題・ブロック図・シミュレーションを選び、操作と期待結果を記録する。
4. TypeScript確認、開発サーバー、ビルド後配信をそれぞれ実行し、現在の成功・失敗を記録する。既に失敗するものは原因を分け、基準画像を作る前に必要な修正を行う。
5. 親、各サブモジュール、robotのコミット・未コミット変更・未追跡ファイルを記録する。履歴やファイルの移行対象を明らかにする。

初期のdocs/features.mdには、algebraの簡約、planeの作図、diagramのブロック実行、gameの採点、movieの教材再生、WebGPU定義追加、保存・認証、robotの通信・診断を載せる。

plotの実装不足、lessonの@let、mediaのコメントアウト部分、diagramの無効なセンサー取得と対応サーバー不在は、既存文書とソースを照合して扱いを明記する。未実装機能を今回まとめて実装する前提にはしない。

## P1: 回帰テストとアニメーションの検証

### 最初のテスト

[index.html](../index.html)のリンクから5アプリを開く。初期化完了を確認し、代表操作を実行する。非同期処理の完了を明示的に待ち、固定秒数の待機への依存を減らす。

| アプリ | 固定する入力と操作 | 判定対象 |
|---|---|---|
| algebra | 検証用数式・証明データを読み、簡約・式変形を行う | 数式・木構造・表示 |
| game | 検証用問題に正解・不正解を入力する | 採点・問題遷移・描画 |
| diagram | 入力・計算・条件・待機の検証用ブロック図を実行・停止する | 出力・実行順・停止・保存復元 |
| movie | 小さな教材を決まった操作まで再生し、停止・再実行する | 図形・数式・強調・順序・リセット |
| webgpu | 小さな定義を固定条件で起動し、決まった区切りまで実行する | 初期化・GPUエラー・数値・描画・停止 |

JavaScript例外と必要な資産のHTTPエラーも記録する。正常に見える画面だけで合格させない。既知のエラーに例外を設ける場合は対象と理由を限定する。

### アプリ内のテスト操作口

- 最小限の仕様は、初期化完了の通知、固定教材の読込、リセット、手動進行、状態の取得、停止とする。名称や型は対象アプリに合わせて設計する。
- 通常の画面、開発用診断パネル、自動テストから同じ再生・計算処理を使う。テスト専用の別実装で期待結果を作らない。
- 時計・乱数・音声・保存先を差し替えられるようにする。テスト設定によって通常の検証・エラー処理が省略されないようにする。
- 開発用の操作口は専用モードで公開する。テストケースと期待値はtests配下に置く。公開ビルドでも通常の画面操作を確認する。

movieでは [flow.ts](../movie/ts/flow.ts) の待機と音声終了に依存する進行を、テスト用の時計・音声イベントで制御する。指定の操作完了まで進む方式を先に導入し、必要な場面に時刻指定を追加する。逆方向へ戻る場合は初期化と再実行を基本とし、任意時刻へのシークを一度に作らない。

WebGPUでは [GraphManager.step()](../webgpu/ts/control.ts) とrequestReadback()を活用する。step()はDSLの区切りまで進むため、物理計算の回数との対応を定義ごとに記録する。[main.ts](../webgpu/ts/main.ts)のperformance.now()依存を制御し、時刻・カメラ・初期値・乱数を固定する。読出しは次のstep()で処理されるため、読出すバッファと観測時点を定め、GPU処理完了を待つ。

### 合否の考え方

- 状態: 数式、座標、操作列、保存JSONなどを期待値と比較する。GPUの浮動小数点値は根拠のある誤差範囲で比較する。
- 時間的な動作: 複数の操作完了時点・フレームで順序、移動、強調、停止後の状態を比較する。
- 描画: 同じOS・ブラウザ・画面サイズ・フォント・描画条件で画像を比較する。基準画像は動作を確認してから登録し、差分を見て更新する。
- 数値モデル: 小さな既知解、参照計算、有限値、モデルに適した保存量・境界条件を確認する。画像の一致だけで物理的妥当性を判定しない。

開発サーバーとビルド後の配信の両方を対象にする。GPU未対応の環境は「未実行」として記録し、対応環境での実行結果を別途必須とする。Firebaseは固定データ・エミュレーターなどを用い、実サービスとの連携確認も別に記録する。

まず5アプリ各1シナリオと、diagramから他アプリを起動して戻る連携を対象にする。WebGPUの14種類のschemaと従来デモは段階的に対象を増やす。テスト対象外も一覧に残す。

## P2: 単一リポジトリ化とビルド整理

- 移行時はalgebra、planeなどの現在のフォルダー配置を保つ。Git管理の変更とソースの責任分割を別の変更として扱う。
- 履歴を統合する方式を第一候補とする。各リポジトリの過去の履歴・ブランチ・タグを保存し、統合する履歴の範囲と旧コミットとの対応を記録する。元リポジトリを保持した検証用コピーで移行手順を試す。
- 現行ソース、必要な資産、未コミット変更、未追跡ファイルを移行後と照合する。robot/chatには未追跡の実装があるため、コミット済みファイルだけを取り込む方法では不足する。
- [package.json](../package.json)のgit submodule foreach依存を置き換え、workspaces、TypeScript参照、公開資産コピーの対象を整理する。plotなどの扱いは明示する。
- JavaScript側はnpmを基準に依存管理を揃える案を検討する。robot/chatのpnpmからの変更は依存と既存テストを確認して別途行う。ESP32のPlatformIOは継続する。
- 共通の確認コマンドを作り、型確認・対象テスト・公開用ビルド・ビルド後のブラウザ確認をつなぐ。例えばnpm run verifyという名称を使う案であり、現在このコマンドが存在するとは扱わない。

完了条件は、通常のcloneから必要な手順で全体を準備でき、P1の確認が再現し、サブモジュール操作に依存しないこと。公開・pushや旧リポジトリの廃止は、この移行検証とは別の作業として扱う。

## P3: 共通入口と起動・終了の整理

1. app/ts/main.tsなどに共通入口を置き、[diagram/ts/index.ts](../diagram/ts/index.ts)のURLによる振り分けを移す。最初は現行URLとHTMLを維持する。
2. diagramの実行処理・停止状態を入口から分け、procedure.tsとの相互importを整理する。
3. import時のDOM取得や初期化を、明示的な初期化処理へ移す。必要なDOM・サービスを起動側から渡す。
4. 機能に応じて初期化、開始、停止、破棄を定義する。イベント、タイマー、音声、GPU資源などの終了処理を整理し、再実行と画面切替を確認する。
5. 初期化済み・失敗の状態を管理する。遅延読込はこの境界が整ってから必要な場所に導入する。

完了条件は、5アプリの直接起動・ルートからの起動・diagram経由の連携で、初期化重複や停止漏れがなく、代表操作の結果が維持されること。

## P4: 循環参照対策を保つ責任分割

- all_functions.tsから、独立した計算を先に取り出す。次に関係管理、保存復元、再生、画面イベントを、依存関係を調べながら分ける。
- 型だけの依存はimport typeとする。実行時に相互依存する処理は、共通部分の抽出、小さなサービス型と実装の接続、密接なクラスの同居を選ぶ。
- AppServicesを図形生成、プロパティ表示、テキスト処理などの役割に整理する。必要な機能だけを利用側へ渡せるようにし、接続を起動側で行う。
- 移行中の互換用再exportを使っても、新しく分けた内部モジュールからall_functions.tsや全体のindex.tsを再び参照しない。
- 依存解析では型の循環と実行時の循環を区別する。全循環の一律禁止を目的にしない。初期化時の評価と継承などを確認する。
- i18nの翻訳、音声、ベクトル、UI・汎用処理と、firebaseの保存処理・画面処理を順番に整理する。外部の利用側には公開APIを設ける。
- GlobalStateの全面廃止を一度に行わず、再実行・画面切替に影響する状態から管理範囲とリセットを明確にする。

完了条件は、変更した機能の所在をfeatures.mdから追え、影響する回帰テストが通り、初期化順への新しい依存が増えないこと。分割の単位は行数ではなく責任と依存関係で判断する。

## P5: robotの全機能の取り込み

最初に既存機能の対応表を作り、移行先と検証結果を記録する。現在の機能を一つずつ取り込み、その後に新しい連携を追加する。

| 既存のまとまり | uroaでの役割 | 確認内容 |
|---|---|---|
| chatの質問画面・Express API | AI質問画面とサーバー | 入力検証、回答・エラー、二重送信抑止、既存APIテスト |
| BLE接続・サーボ操作 | 実機接続サービスと操作画面・ブロック | 指令形式、直列化、ACK、再接続、ARM・MOVE・DISABLE・STOP |
| IMUの表示・グラフ・CSV | センサー表示と教材入力 | 単位変換、通知頻度、欠番、CSV |
| BLEファームウェア | サーボ・IMU用ESP32プロジェクト | ビルド、通信、範囲、切断・タイムアウト・停止 |
| DCモーター復旧確認 | 診断用画面案内と独立したESP32プロジェクト | シリアル指令、エンコーダー、IMU、2秒経過と手動停止 |

### 統合の進め方

1. robotのコード・文書・既存テストを機能ごとに取り込み、実行方法を維持する。候補の置き場はrobot関連のブラウザモジュール、server/、firmware/。最初から全フォルダーを移動する必要はない。
2. ロボット操作のサービス型を定め、BLE実装と模擬実装を用意する。対応機能を明示し、現在BLEにないDCモーター操作を実装済みとして扱わない。
3. diagramのサーボブロックから接続・角度指令・停止までを通す。その後、IMU表示とセンサー入力を接続する。既存HTTP方式の用途を確認して置換・併存を決める。
4. AI質問画面を追加する。APIキーを使う処理はサーバーに置く。AndroidからAPIに到達する配信構成を確認する。現行の127.0.0.1:3001とViteプロキシだけでAndroid・公開環境に対応すると扱わない。
5. 対象のESP32とWindows／Android端末で、通常操作、停止、切断、再接続を確認する。指令角度と実測角度、IMU生値と姿勢推定を表示・文書で区別する。

BLEとDCモーター復旧確認は別の機器構成・ファームウェアとして取り込む。既存の範囲・停止・ハートビート・指令キューの動作を保持する。教材からAIがロボットを制御する仕組みは、教材の学習目標と操作仕様が具体化してから別の機能として設計する。

完了条件は、robotの既存機能がすべて移行先の一覧に対応し、模擬確認と実機確認の結果が分けて記録されること。実機未確認の機能を完成済みとしない。

## P6: 継続的な確認と文書

- 日常の変更では5アプリの基本確認と、変更した処理のテストを実行する。影響が広い変更では関連する連携・シミュレーションの確認を加える。
- 実機不要の確認をCIへ載せ、GPUが必要な確認を対応環境で行う。ファームウェアのビルドと実機操作の確認を分ける。
- タッチ操作や画面配置に関わる変更ではAndroid実端末も対象とする。ブラウザで画面サイズを変える確認と実端末確認を分ける。
- 失敗時は操作履歴、エラー、スクリーンショット差分、数値差分を残す。意図した仕様変更は期待値・文書も同じ変更で更新する。
- AGENTS.mdは作業案内、architecture.mdは現行構成、features.mdは機能索引、この文書は作業案・進捗として役割を分ける。実装時に各項目の状態と検証条件を記録する。

## 最初の作業範囲と保留する判断

最初の成果物は、機能索引、5アプリの現状確認表、固定した代表シナリオ、最小限のブラウザテストとする。アニメーションの手動進行・状態取得は、このシナリオに必要な範囲から導入する。

P0・P1の結果を見て、履歴取り込み方式、既知の不具合の修正範囲、最終配置、依存管理の統一方法を具体化する。教材仕様、AIと実機操作の関係、2種類のファームウェアの将来的な連携は、現段階では決定済みとしない。
