## 現在の優先順位と長期目標（2026-10-12）

ユーザーは、2026-10-16までに簡単なロボット＋AIのデモを作る必要があると明示した。このデモを最優先とし、P4の継続的な責任分割と全面的なrobot取り込みは、デモ成立に必要な部分だけ進める。期限までに全体統合を完成させる計画ではない。

デモは既存のrobotのAI画面・API、ESP32制御を再利用する方向で開始した。2026-10-12のユーザー指定により、diagramでのAIチャット（InputTextBlock・チャットブロック・TTSBlock）と、ServoMotorBlockによる指定角度の操作・IMUBlock／グラフブロックによる計測表示を独立した2つのデモとして作る。AIが定型動作を選んでサーボを操作する機能は不要。音声認識は余裕があれば追加する。2026-10-13の後続指示で、AI部分は学習者自身のキーをAIChatBlockで一時保持し、APIサーバーを使わずGoogleへ直接送る教材向けの構成に変更した。キーを保存・コピー・ログへ含めない。

実機はESP32、PCA9685、SG90、MPU-6050／GY-521で、IMU取得はユーザー確認済み。本人のAndroidタブレットで動作を見せ、携帯電話のアクセスポイント経由でインターネットに接続する。他人への共有・操作やログインはデモ要件に含めない。AndroidのHTTPS公開・AIバックエンド配置が難しい場合はWindows PC＋ローカルViteを使う。公開先・実機サーボ・最終的な完了条件は別途確認する。

最初の実装としてdiagram/ts/ble-wifi/ble.tsにBLEConnectionBlockを追加した。canvasボタンから機器選択・接続・切断を行う。接続ブロックだけではサーボ／IMU出力を開始しない。続くIMUBlock・PlotBlockの実装は下記のとおり。2026-10-13にServoMotorBlockをdiagram/ts/hardware/servo.tsへ移し、明示ARM、角度入力からのMOVE、CH・移動時間、DISABLE/STOPを追加した。接続・再接続だけではサーボを有効化せず、停止時は待機中の古い指令を取り消す。同日にユーザーはサーボの実機確認・commit・pushを報告した。エージェントの模擬確認とは区別する。

同日、InputTextBlock → AIChatBlock（FunctionBlock）→ TTSBlockを実装した。uroaの `/api/ask` 限定プロキシから既存robot/chatのExpress・Interactions APIを再利用する。Startで回答全文を待ち、成功時だけTTSへ渡す。送信状態・回答・エラー、中断と遅延応答の抑止、コピー・JSON配線復元に対応し、ライブの回答は保存しない。Googleまでの実通信1問とTTSの音声出力直前まで確認した。音声出力は模擬で、実際に聞こえること、Android、HTTPS公開は後続確認。操作と検証は [build-and-test.md](build-and-test.md) を参照する。

後続指示による現行実装は、AIChatBlock内の接続ボタンからキー・モデル名を入力し、Googleのモデル情報を取得して接続を確認する。キーをprivateフィールドに保持し、Startごとに再利用する。切断・削除・Clear・読込・pagehide・破棄で解除する。質問はInteractions APIのRESTへ直接送信し、Viteの `/api/ask` プロキシは解除した。ブラウザーでGoogle接続確認・実質問1問・TTSの音声出力直前まで成功した。従来のExpress方式の確認結果は初期実装の記録として扱う。

ユーザーはBLE接続を確認してcommit・pushしたと報告した。続いて、IMUなどの複数値を1本の接続線で渡す構造体入出力を必須と指定した。既存Structを使い、IMUはgyro: vec3とacc: vec3を持つ。CalcBlockの式によるフィールド参照・構造体計算も必要で、if文・whileループは不要。汎用構造体と計算は10月16日に間に合わなくてもよいが、今後のIMU・Port・グラフ修正を6数値ポートに固定せず、この方針に沿わせる。[構造体ポートと式評価の設計案](diagram-struct-design.md)に現行ソースの制約と未実装の提案を記録する。

構造体の初回実装としてdata_type.ts・StructPort・IMUBlockを追加した。IMUBlockの配置／BLE接続で10Hzの通知を受け、gyro・accを1つのポートから出力してconsoleへ表示する。ユーザーはIMUの動作確認とcommit・pushを報告した。続いてPortの有効型取得・配線通知と、汎用PlotBlockを追加した。Structの数値Fieldを読み、IMUならgyro・accを横並び、x/y/zをRGBで表示する。直近30秒の平均・σを1秒ごとに再計算して3σの縦軸範囲を決める。単位・CalcBlockの構造体評価・式の型推論・3D表示は後続作業。検証は模擬と実機を区別して記録する。

長期的な目標は次の3つである。

1. planeの再生方法、diagramのActionBlock、gameのSequencerを統合する。
2. algebraの数式の導出のUIと、planeの作図のUIを統合する。
3. algebra・webgpu・game・diagram・movieの機能を統合した教材作成ツールを作る。

長期目標の実現方式・保存形式・移行順序は未決定。planeの再生処理を必要以上に細分化する作業は先行させない。デモ後のP4は、プロパティ表示・編集、画面イベント、図形・命題生成、AppServicesの役割整理を候補とし、再生の共通化に必要な範囲を見て再開する。

直近のplaneの再生実行分離については、ユーザーが再生テストを実施してcommit・pushしたと報告した。エージェントが確認したのはビルド・成果物であり、全機能や実機の動作確認とは区別する。

新しいチャットでは、この節と両プロジェクトのAGENTS.mdを先に読み、必要な既存ソースとrobotの設計文書を確認する。以前のチャット全文やメモリだけを仕様の記録にしない。

## P1: 回帰テストとアニメーションの検証

### 最初のテスト

[index.html](../index.html)のリンクから5アプリを開く。初期化完了を確認し、代表操作を実行する。非同期処理の完了を明示的に待ち、固定秒数の待機への依存を減らす。

| アプリ | 固定する入力と操作 | 判定対象 |
|---|---|---|
| algebra | 検証用数式・証明データを読み、簡約・式変形を行う | 数式・木構造・表示 |
| game | 検証用問題に正解・不正解を入力する | 採点・問題遷移・描画 |
| diagram | 入力・計算・条件・待機の検証用ブロック図を実行・停止する | 出力・実行順・停止・保存復元 |
| movie | 小さな教材を決まった操作まで再生し、停止・再実行する | 図形・数式・強調・順序・リセット |
| webgpu | 小さな定義を固定条件で起動し、決まった区切りまで実行する | 初期化・GPUエラー・数値・描画・停止 |

JavaScript例外と必要な資産のHTTPエラーも記録する。正常に見える画面だけで合格させない。既知のエラーに例外を設ける場合は対象と理由を限定する。

### アプリ内のテスト操作口

- 最小限の仕様は、初期化完了の通知、固定教材の読込、リセット、手動進行、状態の取得、停止とする。名称や型は対象アプリに合わせて設計する。
- 通常の画面、開発用診断パネル、自動テストから同じ再生・計算処理を使う。テスト専用の別実装で期待結果を作らない。
- 時計・乱数・音声・保存先を差し替えられるようにする。テスト設定によって通常の検証・エラー処理が省略されないようにする。
- 開発用の操作口は専用モードで公開する。テストケースと期待値はtests配下に置く。公開ビルドでも通常の画面操作を確認する。

movieでは [flow.ts](../movie/ts/flow.ts) の待機と音声終了に依存する進行を、テスト用の時計・音声イベントで制御する。指定の操作完了まで進む方式を先に導入し、必要な場面に時刻指定を追加する。逆方向へ戻る場合は初期化と再実行を基本とし、任意時刻へのシークを一度に作らない。

WebGPUでは [GraphManager.step()](../webgpu/ts/control.ts) とrequestReadback()を活用する。step()はDSLの区切りまで進むため、物理計算の回数との対応を定義ごとに記録する。[main.ts](../webgpu/ts/main.ts)のperformance.now()依存を制御し、時刻・カメラ・初期値・乱数を固定する。読出しは次のstep()で処理されるため、読出すバッファと観測時点を定め、GPU処理完了を待つ。

### 合否の考え方

- 状態: 数式、座標、操作列、保存JSONなどを期待値と比較する。GPUの浮動小数点値は根拠のある誤差範囲で比較する。
- 時間的な動作: 複数の操作完了時点・フレームで順序、移動、強調、停止後の状態を比較する。
- 描画: 同じOS・ブラウザ・画面サイズ・フォント・描画条件で画像を比較する。基準画像は動作を確認してから登録し、差分を見て更新する。
- 数値モデル: 小さな既知解、参照計算、有限値、モデルに適した保存量・境界条件を確認する。画像の一致だけで物理的妥当性を判定しない。

開発サーバーとビルド後の配信の両方を対象にする。GPU未対応の環境は「未実行」として記録し、対応環境での実行結果を別途必須とする。Firebaseは固定データ・エミュレーターなどを用い、実サービスとの連携確認も別に記録する。

まず5アプリ各1シナリオと、diagramから他アプリを起動して戻る連携を対象にする。WebGPUの14種類のschemaと従来デモは段階的に対象を増やす。テスト対象外も一覧に残す。

## P2: 単一リポジトリ化とビルド整理

- 移行時はalgebra、planeなどの現在のフォルダー配置を保つ。Git管理の変更とソースの責任分割を別の変更として扱う。
- 履歴を統合する方式を第一候補とする。各リポジトリの過去の履歴・ブランチ・タグを保存し、統合する履歴の範囲と旧コミットとの対応を記録する。元リポジトリを保持した検証用コピーで移行手順を試す。
- 現行ソース、必要な資産、未コミット変更、未追跡ファイルを移行後と照合する。robot/chatには未追跡の実装があるため、コミット済みファイルだけを取り込む方法では不足する。
- [package.json](../package.json)のgit submodule foreach依存を置き換え、workspaces、TypeScript参照、公開資産コピーの対象を整理する。plotなどの扱いは明示する。
- JavaScript側はnpmを基準に依存管理を揃える案を検討する。robot/chatのpnpmからの変更は依存と既存テストを確認して別途行う。ESP32のPlatformIOは継続する。
- 共通の確認コマンドを作る。現在の `npm run verify` は型確認・公開用ビルド・成果物の静的確認を行う。大規模ブラウザテストは `npm run test:e2e` で別途実行する。サーバーの自動起動とブラウザ確認の一括実行は後続の検討事項。

完了条件は、通常のcloneから必要な手順で全体を準備でき、P1の確認が再現し、サブモジュール操作に依存しないこと。公開・pushや旧リポジトリの廃止は、この移行検証とは別の作業として扱う。

P0・P1の結果を見て、履歴取り込み方式、既知の不具合の修正範囲、最終配置、依存管理の統一方法を具体化する。教材仕様、AIと実機操作の関係、2種類のファームウェアの将来的な連携は、現段階では決定済みとしない。
