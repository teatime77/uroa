# コーディング規約

2026-10-27に指定された書式。以降、uroaで新規作成・変更するコードはこの規約に従う。既存コードを整形する範囲は作業の対象に合わせる。

ESP32の現行教材・共有ライブラリーは別リポジトリーの`D:\usr\prj\esp32`で管理し、[同リポジトリーの規約](../../esp32/docs/coding-style.md)と[.clang-format](../../esp32/.clang-format)に従う。uroa内の旧ESP32フォルダーは廃止対象で、現行の整形設定の参照先にしない。`.pio/`内の外部ライブラリーとビルド生成物は編集対象から除く。Doxygenコメントの内容と変数宣言の分割は、整形ツールとは別に確認する。

## 実装の基本方針

- ESP32はメモリー容量と処理速度に制限があることを前提に設計する。必要な機能を満たす単純な実装を優先し、不要なコピー・一時領域・動的確保・全件探索を増やさない。
- これは教材である。生徒が処理の流れ、データの配置、値の変化を追って理解しやすいコードにする。短く書くことより、素直な制御構造と分かりやすい名前を優先する。
- 現在必要な機能の範囲で実装し、将来の機能を想定した過剰な汎用化・抽象化・管理情報を追加しない。
- 検査はその条件を保証する責任のある箇所で行い、保証済みの不変な情報を各層で繰り返し検査しない。外部入力や実行時の添字範囲など、実行時に必要な検査は行う。
- 関数分割・共通化・テンプレートは、処理の重複を減らし、生徒が理解しやすくなる場合に使う。処理を追いにくくする共通化より、短い型別処理を選ぶ。

## コメント

### 仕様の記述先

- TypeScript・C++を含むすべてのソースファイルで、以降、新規追加・変更する仕様はすべてソースのコメントへ記述する。実装と同時にコメントを追加・更新することを必須とする。
- 単一ファイル内の仕様は、そのソースの該当する宣言・処理に対応するコメントへ記述する。
- 複数のソースファイルに関係する仕様は、中心的なソースファイルの関連するコードの近くへ記述し、関係するファイルと役割を示す。ソース全体に関する説明だけを先頭へ記述する。関連ファイルから参照を示す場合も、仕様本文は中心的なソースにまとめる。
- 仕様コメントには、対象の役割・公開API・入出力・データ形式・制約・未対応範囲など、その実装の仕様を記述する。仕様を設計文書へ追加・重複記載しない。既存文書と異なる場合はソースの仕様コメントを参照する。
- 作業開始時に対象ソースと中心的なソースの仕様コメントを読み、完了時に実装とコメントの一致を必ず確認する。

### コメントの配置

- コメントは、説明する宣言・関数・処理など、関連するコードの近くに記述する。関数全体の仕様は関数の直前、関数内の特定の処理に関する説明はその処理の直前に置く。
- ソースファイルの先頭には、ファイルの役割や他のファイルとの分担など、特定のコードではなくソース全体に関するコメントだけを記述する。
- 個別の処理の仕様や制約をファイル先頭へまとめない。コードを読んだ位置で、その処理の目的・前提・制約を確認できるようにする。

### コメントの形式

C++のファイル、関数、クラス、構造体にはDoxygen形式のコメントを書く。説明は日本語を基本とし、関数には目的を`@brief`、引数を`@param`、戻り値を`@return`で記載する。戻り値のない関数には`@return`を書かない。必要に応じて`@details`に呼出元タスク、単位、状態の変更、副作用や制約を記載する。変数・メンバーの短い説明には`///<`を使える。他言語では、その言語に対応した文書コメント形式を使う。

Doxygenのブロックコメントは複数行で記述し、開始の`/**`と終了の`*/`をそれぞれ独立した行に置く。`@file`・`@brief`・`@param`・`@return`・`@details`などのタグは、タグごとに別の行へ記述する。複数のタグやブロック全体を1行にまとめない。大域変数・メンバー変数にはすべて説明を付け、短い説明の`///<`は宣言と同じ行に記述してよい。

```cpp
/**
 * @brief センサーの生データを角速度へ変換する。
 * @param raw 符号付きの生データ。
 * @return 角速度。単位は度/秒。
 */
float angularRate(int16_t raw) {
    return raw / 131.0f;
}
```

## ブロックとインデント

- `if`のthen節、`else if`と`else`の各節を必ず`{}`で囲む。処理が1文でも省略しない。
- `for`、範囲for、`while`、`do`のループ本体も必ず`{}`で囲む。
- ブロックを開く`{`の直後で改行する。閉じる`}`は独立した行に置く。`};`やラムダ式の`});`など、構文上必要な末尾は同じ行に置ける。
- インデントはスペース4個とし、ブロックの内側を1段深くする。タブは使わない。関数、名前空間、型、ラムダ式の本体にも同じ規則を使う。
- `else`と`else if`は直前の`}`の次の行に置く。
- `switch`の`case`・`default`は`switch`の内側へ1段、その処理はさらに1段インデントする。

変数の`{}`初期化や配列・集成体の初期化リストは、処理ブロックとは区別する。例えば`uint8_t raw[14]{};`は1行で書ける。

```cpp
if (connected) {
    startStream();
}
else {
    stopStream();
}

for (int index = 0; index < count; ++index) {
    if (samples[index].valid) {
        process(samples[index]);
    }
}

while (waiting) {
    poll();
}
```

## 意味を持つ数値

- 命令番号・状態番号・操作種別・ビットフラグなど、意味を持つ数値はenumや名前付き定数で定義する。
- 定義箇所以外では数値を直接記述せず、`switch`の`case`、条件式、フラグ操作などに名前を使う。例えば`case 0x01:`ではなく`case Opcode::LOAD_L:`とする。
- 複数のファイルで使う定義は共通の宣言元にまとめる。通信形式や保存形式の既存の数値は維持し、名前・値・役割をコメントに記載する。

## 文と変数宣言

- 1行に複数の文を書かない。文末の`;`の後で改行する。
- `return`、`break`、`continue`も別の文と同じ行に書かない。
- 1行に複数の変数を宣言しない。カンマで宣言を連結せず、変数ごとに型を付けて別の行に書く。構造体のメンバーにも適用する。
- `for`ヘッダーの`;`は文末ではなく構文上の区切りなので、ヘッダーは1行で書ける。ヘッダー内で宣言する変数も1個とする。
- 関数の引数や初期化リストのカンマは複数変数の宣言とは区別する。

```cpp
uint32_t previous = micros();
uint32_t lastCommand = millis();
const bool stopped = mustStop.exchange(false);
const bool urgent = urgentStop.exchange(false);

controller.stop();
wheels.off();

if (stopped || urgent) {
    streamHz = 0;
    return;
}
```
